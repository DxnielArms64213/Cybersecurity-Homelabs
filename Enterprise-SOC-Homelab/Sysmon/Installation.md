# Sysmon Installation

## Overview

Microsoft Sysmon (System Monitor) was installed on the `WIN-CLIENT` Windows endpoint to provide detailed system telemetry for the Enterprise SOC Homelab.

Sysmon extends the information available from standard Windows event logging by recording detailed events such as:

* Process creation
* Network connections
* Process termination
* File creation
* Registry activity
* Driver and image loading
* Other system activity depending on the configured rules

The telemetry generated by Sysmon provides an important data source for the Wazuh monitoring infrastructure.

Sysmon was installed directly on the Windows Client because it is the endpoint being monitored by the SOC.

## Configuration Source

The Sysmon configuration used in the lab was the **SwiftOnSecurity Sysmon configuration**.

This configuration provides a practical baseline for security monitoring by selecting useful Sysmon events while reducing unnecessary telemetry.

Using an established configuration also provides a more realistic starting point for the lab than enabling every available Sysmon event without filtering.

## Installation

Sysmon was installed on `WIN-CLIENT` and configured using the SwiftOnSecurity configuration file.

The installation resulted in the Sysmon service being registered on Windows and the configured Sysmon event logging becoming available through Event Viewer.

The configuration was applied during installation so that Sysmon would immediately begin generating the required telemetry.

## Verification

After installation, Sysmon was verified through Windows Event Viewer.

The Sysmon operational log was available under:

```text
Applications and Services Logs
└── Microsoft
    └── Windows
        └── Sysmon
            └── Operational
```

Sysmon events were subsequently observed in the operational log, confirming that the installation and configuration were functioning.

The presence of generated events confirmed that Sysmon was actively collecting endpoint telemetry.

## Event Viewer Access

During verification, an access-denied message was encountered when attempting to access the Sysmon event logs.

This was caused by Event Viewer not being run with sufficient administrative privileges.

Event Viewer was subsequently opened with administrative privileges, after which the Sysmon logs and generated events could be accessed successfully.

This demonstrated an important distinction between:

* Sysmon successfully generating telemetry
* A user having sufficient permissions to view that telemetry

The access issue did not indicate that Sysmon itself had failed.

## Role in the SOC

Sysmon acts as an endpoint telemetry source within the SOC architecture.

The general telemetry flow is:

```text
Windows Activity
       │
       ▼
    Sysmon
       │
       ▼
Sysmon Event Logs
       │
       ▼
 Wazuh Agent
       │
       ▼
 Wazuh Manager
       │
       ▼
Detection / Analysis
       │
       ▼
Wazuh Dashboard
```

Sysmon does not replace Windows Security logs. Instead, it provides additional endpoint telemetry that can be correlated with standard Windows events.

For example, a Windows authentication event may indicate that a user logged in, while Sysmon can provide additional information about processes and network activity occurring on the endpoint.

This combination provides a more useful dataset for detection and investigation.
